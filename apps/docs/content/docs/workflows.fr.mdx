Un workflow fixe les étapes que suit une tâche, qui s’occupe de chacune et ce qu’il faut y faire. Chaque squad utilise un workflow pour les tâches qu’il traite.

Par exemple, un workflow de livraison peut suivre ce parcours :

| Étape | Responsable | Travail à effectuer |
|---|---|---|
| Développement | Un agent de développement | Réaliser les modifications et les préparer pour la revue. |
| Revue | Un agent de revue | Vérifier le résultat, puis le transmettre à la QA ou le renvoyer pour correction. |
| QA | Un membre de l’équipe | Essayer le résultat et décider s’il est prêt à être terminé. |

Passer une tâche en revue la confie à l’agent de revue. La description, les échanges et les résultats précédents restent dans la même tâche pour que le prochain responsable puisse prendre la suite.

Le modèle **Livraison** suit exactement cette structure. Les tâches qui ne sont assignées à aucun squad utilisent **Default** : tous les statuts sont disponibles et rien n’est confié automatiquement, comme auparavant.

## Créer un workflow

Un `owner` ou un `admin` de l’espace de travail peut créer des workflows dans l’application web ou de bureau :

<Steps>
<Step>

Ouvrez **Paramètres → Workflows**, puis **Nouveau workflow**. Partez de zéro ou utilisez le modèle **Livraison**, **Contenu** ou **Communauté**.

</Step>
<Step>

Nommez le workflow et choisissez ses colonnes de statut. Faites glisser les colonnes du milieu dans l’ordre souhaité.

</Step>
<Step>

Sélectionnez une colonne et choisissez ce qui se passe quand une tâche y entre : **Pas de relais**, **Confier à un agent** ou **Confier à un membre**. La liste des membres propose aussi **Responsable du projet**.

</Step>
<Step>

Pour une étape confiée à un agent, écrivez ce qu’il doit faire, puis choisissez **Une fois terminé, passer à** (si vous ne choisissez rien, la colonne suivante, en sautant les colonnes de clôture comme Won't Fix ; une colonne Terminé ou Fermée ne mène nulle part par défaut) et **En cas de rejet, renvoyer à** (quand cette étape juge le travail reçu insuffisant et qu’il doit être repris). Si l’étape ne peut pas continuer pour une raison extérieure, utilisez **Blocked** plutôt que le renvoi ; l’étape renvoie la tâche à la place seulement si le workflow n’a pas de colonne Blocked, ou si elle est elle-même une colonne Terminé ou Fermée.

</Step>
<Step>

Prévisualisez les consignes que l’agent recevra, puis enregistrez.

</Step>
</Steps>

Si vous avez ajouté un nouveau statut, enregistrez d’abord le workflow avant de configurer son passage de relais.

Sans passage de relais, le responsable ne change pas. Confier la tâche à un membre change le responsable sans lancer d’agent. La confier à un agent lui demande de commencer cette étape. Vous devez avoir le droit de l’appeler et son ordinateur doit être en ligne pour l’exécuter.

## L’utiliser avec un squad

Ouvrez le squad et choisissez son **Workflow**. Les responsables du squad et les `admin` de l’espace de travail peuvent le modifier. La confirmation indique quelles tâches du squad gardent leur statut. Si certaines utilisent un statut absent du nouveau workflow, choisissez où les placer. Changer de workflow ne transmet pas les tâches et ne lance pas d’agent.

Une tâche suit le workflow du squad auquel elle est assignée, ou celui du squad auquel appartient l’agent assigné. Un squad sans workflow ne peut pas recevoir de nouveau travail : quand vous lui assignez une tâche, le formulaire vous demande d’abord de choisir un workflow pour ce squad.

Les projets n’ont pas de workflow propre. Le tableau d’un projet affiche une colonne pour chaque statut utilisé par les workflows des squads qui traitent ses tâches, dans l’ordre de leur première apparition. Le sélecteur de statut de chaque tâche propose les étapes du workflow de son propre squad et indique qui prend le relais.

### Tâches qui ne sont pas des demandes d’un squad à flux

Un squad dont le workflow est un flux exécute ses propres demandes sur ce flux. Les autres tâches de ce squad, comme les sous-tâches, suivent le choix de l’espace de travail défini dans **Paramètres → Workflows** : **Aucune action** (par défaut, qui vous demande la première fois), **Default**, ou un workflow que vous choisissez. Seuls les `admin` de l’espace de travail peuvent le modifier.

## Passer à l’étape suivante

Changez le statut d’une tâche ou faites glisser sa carte vers une autre colonne. Si cette étape prévoit un passage de relais, vérifiez le destinataire et, pour un agent, les consignes qu’il recevra.

<WorkflowDemo />

Quand vous créez une tâche et l’assignez à un squad, et que son statut prévoit un passage de relais dans le workflow de ce squad, elle est confiée directement au responsable de cette étape ; un agent commence aussitôt. La fenêtre de création indique à qui elle sera confiée. Pour la créer sans rien lancer, placez-la dans Backlog.

Si le responsable précédent est un agent dont l’exécution est encore en cours ou en attente, la confirmation propose en plus de l’arrêter ou de l’annuler, option cochée par défaut. Laissez-la cochée, sauf si vous voulez que les deux agents travaillent en même temps ; ses commentaires publiés et le travail déjà enregistré sont conservés.

**Une fois terminé, passer à** et **En cas de rejet, renvoyer à** indiquent à l’agent où déplacer la tâche ensuite. La fin d’une exécution ne fait pas avancer la tâche à elle seule : c’est le membre ou l’agent responsable de l’étape qui met à jour son statut. Quand un agent fait entrer la tâche dans l’étape suivante, le passage de relais de cette étape se déclenche de la même façon.

Le passage de relais et ses consignes restent dans l’historique de la tâche. Le menu du workflow sur le tableau du projet permet d’afficher le parcours complet.

## Ajuster un workflow

Plusieurs squads peuvent partager un workflow. Les modifications enregistrées dans **Paramètres → Workflows** s’appliquent à tous les squads qui l’utilisent. Pour changer le parcours d’un seul squad, dupliquez le workflow et choisissez la copie dans ce squad.

Les administrateurs peuvent aussi configurer un passage de relais depuis le tableau du projet : survolez l’en-tête d’une colonne et cliquez sur **Confier à…**, ou sur le responsable déjà affiché. La modification s’applique à toutes les tâches des squads qui utilisent ce workflow.

Retirer une colonne peut vous demander de choisir un nouveau statut pour les tâches qui s’y trouvent. Les autres restent en place et ce déplacement ne lance pas d’agent. La bibliothèque de statuts, sous la liste des workflows, permet de modifier les noms et les couleurs ; ces changements s’appliquent partout où le statut est utilisé.

Pour supprimer un workflow, passez d’abord les squads qui l’utilisent à un autre workflow. Les tâches gardent leur statut actuel.

Si **Paramètres** ne contient pas **Workflows**, la fonctionnalité n’est pas encore disponible dans cet espace de travail ; les statuts se gèrent toujours dans **Paramètres → États des tâches**.
